# راهنمای تنظیم سفارش و تحویل هر فروشنده (V2)

این راهنما توضیح می‌دهد چگونه برای هر منبع (فروشنده) بازه‌ی پذیرش سفارش و زمان تقریبی
رسیدن کالا به قزوین را تعریف و ویرایش کنید. همه‌ی محاسبات بر مبنای منطقه‌ی زمانی
`Asia/Tehran` است و تنظیمات هر فروشنده **کاملاً مستقل** از بقیه اعمال می‌شود.

## فایل تنظیمات

`config/delivery.yaml` (پروفایل آفلاین/نمونه) و `config.real/delivery.yaml` (پروفایل واقعی).

اگر منبعی در این فایل نباشد یا فایل وجود نداشته باشد، خروجی آن منبع
«زمان تحویل نامشخص» است و هیچ منبع دیگری دچار اختلال نمی‌شود. خطای ساختاری در فایل
(کلید ناشناخته، ساعت نامعتبر و…) در گزارش چرخه هشدار داده می‌شود و قیمت‌ها بدون تحویل ادامه می‌یابند.

## ساختار کامل

```yaml
timezone: Asia/Tehran
sources:
  eways:
    order_windows:                    # یک یا چند بازه سفارش در روز
    - start: "09:00"                  # شروع پذیرش سفارش
      end: "12:00"                    # ساعت قطع سفارش (Cut-off) — دقیقاً در این ساعت هم پذیرفته می‌شود
      ship_at: "13:30"                # ساعت تقریبی ارسال
      delivery_at: "18:00"            # ساعت تقریبی رسیدن به قزوین
      delivery_day_offset: 0          # ۰ = همان روز، ۱ = روز بعد، ...
      note: "سفارش‌های بعدازظهر به روز کاری بعد منتقل می‌شود"
    active_weekdays: [saturday, sunday, monday, tuesday, wednesday, thursday]  # روزهای کاری
    holidays: ["2026-03-20"]          # تعطیلات خاص (YYYY-MM-DD)
    verified: false                   # true = تاییدشده توسط فروشنده، false = تخمینی
    note: "توضیح آزاد درباره‌ی ارسال"
    shipping_cost_toman: 80000        # اختیاری — هزینه ارسال جدا از قیمت گوشی
    shipping_note: "نیازمند استعلام"  # اگر هزینه ثابت ندارد
```

### نکات مهم

- **«فردا»، «امروز» و روز هفته** در گزارش‌ها نسبت به لحظه‌ی استعلام سنجیده می‌شوند.
- اگر ساعت استعلام از `end` (قطع) گذشته باشد، نزدیک‌ترین بازه‌ی معتبر بعدی در اولین
  روز کاری آینده محاسبه می‌شود؛ تعطیلات هفتگی و `holidays` رعایت می‌شوند.
- اگر `delivery_day_offset: 0` باشد و `delivery_at` بعد از `ship_at` نباشد، خطای
  پیکربندی می‌گیرید (زمان رسیدن نمی‌تواند قبل از ارسال باشد).
- زمان‌های `verified: false` همیشه با برچسب **«(تقریبی)»** نمایش داده می‌شوند و هرگز
  به‌عنوان زمان قطعی معرفی نمی‌شوند.
- اگر هزینه ارسال تعیین نشده باشد، خروجی «هزینه ارسال نیازمند استعلام» می‌دهد؛ هزینه ارسال
  همیشه از قیمت گوشی جدا گزارش می‌شود.

## چند بازه سفارش در روز

```yaml
sources:
  my_shop:
    order_windows:
    - {start: "09:00", end: "12:00", ship_at: "13:00", delivery_at: "17:00", delivery_day_offset: 0}
    - {start: "15:00", end: "18:00", ship_at: "19:00", delivery_at: "11:00", delivery_day_offset: 1}
```

سفارشی که قبل از ۱۲ بازه‌ی اول را می‌گیرد و سفارش ساعت ۱۴ به بازه‌ی دوم (۱۵ تا ۱۸) می‌رود.

## منطق «سریع‌ترین فروشنده»

برای هر رنگِ هر محصول، منبعی که زودترین زمان رسیدن به قزوین را دارد «سریع‌ترین» است؛
اگر دو فروشنده هم‌زمان بودند، قیمت کمتر اولویت دارد. اختلاف زمان تحویل «سریع‌ترین» با
«ارزان‌ترین» و اختلاف قیمت آن دو، در خروجی JSON (`deltas`) و گزارش‌ها نمایش داده می‌شود.

## مقادیر اولیه‌ی پروژه

ساعت‌های نوشته‌شده در `config/delivery.yaml` و `config.real/delivery.yaml` برای
eways/hamrahtel/farnaa/exontel/kasrapars/digikala_b2b **نمونه‌ی تخمینی** هستند (همه
`verified: false`). پس از استعلام از هر فروشنده، آن‌ها را اصلاح کنید و فقط زمانی که
فروشنده تایید کرد `verified: true` بگذارید تا برچسب «تقریبی» حذف شود.
